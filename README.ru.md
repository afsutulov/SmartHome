# SmartHome

[English](README.md) · Русский

SmartHome — сервис на Go для автоматизации умного дома через MQTT. Он получает сообщения устройств, хранит локальное состояние, выполняет правила и действия из JSON-конфига, предоставляет управление через Telegram. Работает с ZigbeeMQTTlink или zigbee2mqtt; дополнительно можно подключить yandex2mqtt и внешний видеорегистратор.

Руководство описывает установку, настройку, эксплуатацию и диагностику текущей реализации.

## Архитектура

| Компонент | Задача |
| --- | --- |
| Zigbee-устройства и координатор | Радиообмен, сопряжение и физическое переключение. |
| ZigbeeMQTTlink или zigbee2mqtt | Преобразование сообщений Zigbee в MQTT и команд MQTT в радиокоманды. |
| MQTT-брокер, например Mosquitto | Передача сообщений между сервисами. |
| SmartHome | Правила автоматизации, состояние, команды и уведомления. |
| Telegram-бот | Пользовательское управление и уведомления. |
| yandex2mqtt, необязательно | Голосовые команды и передача состояния внешней интеграции. |
| Видеорегистратор, необязательно | Готовый видеофайл и файл-триггер для отправки. |

SmartHome подключается к MQTT и получает обновления Telegram методом long polling. HTTP-сервера и собственного веб-интерфейса в нём нет; USB-координатор он не открывает. Создание Zigbee-сети, добавление устройств, радионастройки и резервное копирование координатора выполняются в Zigbee-сервисе.

Правило протечки может получить `{"water_leak":true}`, отправить закрытие клапана, включить сирену командой `{"alarm":true}` и поставить уведомление в очередь Telegram.

Успешная публикация MQTT означает завершение операции MQTT. Она **не подтверждает**, что клапан физически закрылся или сирена зазвучала.

## Требования и файлы

Для работы необходимы:

- Доступный MQTT-брокер с правами на нужные подписки и публикации.
- Настроенный Zigbee-сервис, уже публикующий сообщения ваших устройств.
- Токен Telegram-бота и разрешённые Telegram ID пользователей.
- Каталог состояния с правом записи; при файловом журналировании — также каталог журналов.
- Исходящий доступ к Telegram напрямую либо через SOCKS5.

Непустой токен обязателен даже при использовании преимущественно MQTT-автоматики. Пустой массив `allowed_users` допустим, но бот будет игнорировать всех пользователей. Обработка MQTT и расписания запускаются до успешного подключения к Telegram.

Поставляемые бинарники:

| Платформа | Архитектура | Файл |
| --- | --- | --- |
| Linux | x86-64 / AMD64 | `bin/linux-amd64/SmartHome` |
| Linux | ARM64 / AArch64 | `bin/linux-arm64/SmartHome` |
| Windows | x86-64 / AMD64 | `bin/windows-amd64/SmartHome.exe` |

ARMv7 не включён в скрипт сборки поставки. Go нужен для сборки исходников, но не для запуска готового бинарника. В модуле указана минимальная версия Go 1.25 и запрошен toolchain Go 1.26.8; при автоматическом выборе инструментария первая сборка может загрузить его.

Рекомендуемые пути Linux:

| Путь | Назначение и права |
| --- | --- |
| `/usr/local/bin/SmartHome` | Бинарник: `root:root`, `0755`. |
| `/etc/smarthome.conf` | JSON-конфиг с учётными данными: `root:smarthome`, `0640`. |
| `/var/lib/smarthome/state.json` | Состояние; записывает пользователь `smarthome`, новые сохранения имеют права `0600`. |
| `/var/log/smarthome/smarthome.log` | Необязательный журнал; каталог доступен `smarthome` для записи. |
| `/etc/systemd/system/smarthome.service` | Юнит сервиса: `root:root`, `0644`. |

Расширение `.conf` — только соглашение об имени. Содержимое файла должно быть JSON.

## Быстрый запуск

Выполняйте команды из корня распакованного проекта. Для Linux x86-64:

```bash
uname -m
chmod +x bin/linux-amd64/SmartHome
mkdir -p run
chmod 700 run
cp configs/smarthome.conf.example.json run/config.json
```

Для ARM64 замените `linux-amd64` на `linux-arm64`. Для первого теста подключения замените скопированный конфиг минимальным объектом ниже. Укажите настоящий токен и свой ID:

```json
{
  "telegram": {
    "token": "REPLACE_WITH_BOT_TOKEN",
    "welcome_message": "SmartHome готов к работе.",
    "allowed_users": [
      {"id":111111111,"video_monitoring_enabled":false}
    ]
  },
  "mqtt": {
    "server":"tcp://127.0.0.1:1883",
    "client_id":"SmartHome",
    "qos":1,
    "retained":false,
    "base_topics":["zigbee2mqtt"]
  },
  "storage":{"state_file":"./run/state.json"},
  "logging":{"level":"info","file":"","to_console":true},
  "menu":{
    "start_command":"/start",
    "rows":[[{"text":"Статус","builtin":"status"}]]
  },
  "devices":[],
  "events":[],
  "groups":[],
  "schedules":[],
  "command_integrations":[]
}
```

Пустой список устройств нужен для проверки подключения. Для автоматизации сначала добавьте устройства и события.

```bash
chmod 600 run/config.json
./bin/linux-amd64/SmartHome --check-config --config ./run/config.json
./bin/linux-amd64/SmartHome --run --config ./run/config.json
```

Проверка должна вывести `Configuration OK`. Откройте личный чат с ботом, отправьте `/start` и нажмите **Статус**. Для остановки процесса нажмите Ctrl+C.

`--check-config` проверяет JSON, ссылки, выражения и шаблоны топиков. Он не подключается к MQTT/Telegram, не проверяет учётные данные и оборудование, не подтверждает доступность каталогов для записи.

Запуск без `--run` выводит справку и завершает программу.

## Установка в Linux через systemd

### Подготовьте бинарник

Скопируйте подходящий бинарник в корень проекта:

```bash
install -m 0755 bin/linux-amd64/SmartHome ./SmartHome
```

Для ARM64 вместо предыдущей команды:

```bash
install -m 0755 bin/linux-arm64/SmartHome ./SmartHome
```

Либо соберите из исходников:

```bash
go version
go mod download
go mod verify
go build -o SmartHome .
```

Команда `sha256sum -c SHA256SUMS` проверяет контрольные суммы поставляемых бинарников в Linux.

### Установите сервис

Из корня проекта:

```bash
sudo bash scripts/install-systemd.sh
```

Скрипт ожидает исполняемый файл `./SmartHome`. Он создаёт системного пользователя `smarthome`, каталоги состояния и журналов, устанавливает бинарник и юнит, включает автозапуск. Если конфига ещё нет, устанавливается пример.

Сам сервис скрипт **не запускает**. Содержимое существующего `/etc/smarthome.conf` сохраняется, но владелец и права устанавливаются в `root:smarthome` / `0640`. Владельцем стандартных каталогов состояния и журналов рекурсивно становится `smarthome`; храните в них файлы этого сервиса.

### Настройте и проверьте права

```bash
sudo nano /etc/smarthome.conf
sudo -u smarthome /usr/local/bin/SmartHome --check-config --config /etc/smarthome.conf
sudo -u smarthome test -r /etc/smarthome.conf
sudo -u smarthome test -w /var/lib/smarthome
sudo -u smarthome test -w /var/log/smarthome
```

Если state-файл уже существует:

```bash
sudo -u smarthome test -r /var/lib/smarthome/state.json
```

Для нестандартных путей нужны права на родительские каталоги. Атомарное сохранение состояния и обработка видеотриггеров создают и переименовывают файлы внутри этих каталогов.

Для установки подготовленного конфига используйте команду с явными правами:

```bash
sudo install -o root -g smarthome -m 0640 ./config.json /etc/smarthome.conf
```

Проверьте новый файл до замены рабочего конфига; после установки повторите проверку от имени `smarthome`.

### Запустите и проверьте

```bash
sudo systemctl start smarthome
sudo systemctl status smarthome --no-pager
sudo journalctl -u smarthome -n 100 --no-pager
sudo journalctl -u smarthome -f
```

Юнит выполняет `/usr/local/bin/SmartHome --run --config /etc/smarthome.conf` от пользователя и группы `smarthome`. Рабочий каталог — `/var/lib/smarthome`. При аварийном завершении процесс перезапускается через пять секунд.

Основные команды:

```bash
sudo systemctl stop smarthome
sudo systemctl restart smarthome
sudo systemctl enable smarthome
sudo systemctl disable smarthome
```

Enable/disable управляет запуском после загрузки ОС, а не текущим процессом. После изменения конфига нужен restart; горячей перезагрузки конфигурации нет.

### Ручная установка

Если не используете скрипт, сначала создайте пользователя, если его ещё нет:

```bash
sudo useradd --system --home-dir /var/lib/smarthome --shell /usr/sbin/nologin smarthome
sudo install -d -o smarthome -g smarthome -m 0750 /var/lib/smarthome /var/log/smarthome
sudo install -o root -g root -m 0755 ./SmartHome /usr/local/bin/SmartHome
sudo install -o root -g smarthome -m 0640 ./config.json /etc/smarthome.conf
sudo install -o root -g root -m 0644 systemd/smarthome.service /etc/systemd/system/smarthome.service
sudo systemctl daemon-reload
sudo -u smarthome /usr/local/bin/SmartHome --check-config --config /etc/smarthome.conf
sudo systemctl enable --now smarthome
```

Используйте конфиг с уже проверенными учётными данными, топиками и командами устройств.

## Windows

Сборка из каталога проекта:

```powershell
go build -o SmartHome.exe .
```

Либо запуск готового файла:

```powershell
New-Item -ItemType Directory -Force C:\SmartHome | Out-Null
Copy-Item .\configs\smarthome.conf.example.json C:\SmartHome\config.json
notepad C:\SmartHome\config.json
.\bin\windows-amd64\SmartHome.exe --check-config --config C:\SmartHome\config.json
.\bin\windows-amd64\SmartHome.exe --run --config C:\SmartHome\config.json
```

Укажите Windows-пути в конфиге. Фрагмент:

```json
{
  "storage":{"state_file":"C:/SmartHome/state.json"},
  "logging":{"level":"info","file":"C:/SmartHome/smarthome.log","to_console":true}
}
```

Прямой слеш позволяет избежать экранирования обратных слешей в JSON. Пользователь должен иметь права чтения конфига и записи в выбранные каталоги. Установщик службы Windows не поставляется.

## Параметры командной строки

| Параметр | Назначение |
| --- | --- |
| `--run` | Запустить сервис. |
| `--config PATH` / `-c PATH` | Путь к JSON-конфигу; по умолчанию `/etc/smarthome.conf`. |
| `--check-config` | Проверить конфигурацию без подключений и завершиться. |
| `--version` / `-v` | Показать версию программы и завершиться. |
| `--help` / `-h` | Показать справку. |

Параметры указывайте до позиционных аргументов:

```bash
./SmartHome --version
./SmartHome --help
./SmartHome --check-config -c ./config.json
./SmartHome --run -c ./config.json
```

SIGTERM и SIGINT/Ctrl+C вызывают сохранение состояния и отключение MQTT. Завершение не гарантирует выполнение всех накопленных действий и уведомлений.

## Правила конфигурации

Файл — ровно один JSON-объект в UTF-8. Комментарии, запятые после последнего элемента и неизвестные поля типизированной конфигурации отклоняются. Пример `.jsonc` предназначен для чтения; перед использованием удалите комментарии.

Логические поля задавайте как `true`/`false`, без кавычек. Особенно это важно для команды сирены `alarm`.

| Раздел | Назначение |
| --- | --- |
| `telegram` | Бот, пользователи, опрос и прокси. |
| `mqtt` | Брокер, QoS, retained, топики и подписки. |
| `storage` | Путь к состоянию. |
| `logging` | Уровень и направления журналирования. |
| `labels` | Подписи и формат даты. |
| `video_monitoring` | Наблюдение за видеотриггером. |
| `devices` | Логические устройства, состояния, действия и отчёты. |
| `groups` | Группы и групповые действия. |
| `events` | Правила входящих MQTT-сообщений. |
| `command_integrations` | Внешние источники команд включения/выключения. |
| `menu` | Telegram-клавиатура. |
| `schedules` | Ежедневные действия. |

Выбирайте стабильные уникальные ID устройств/групп без точек, например `bathroom_valve`. Ссылки имеют вид `object_id.action_name`. ID устройств и групп не должны пересекаться. ID событий и ID расписаний должны быть уникальны каждый в своём разделе.

Конфигурация читается при запуске. Подстановки переменных окружения и включения других файлов нет. Секреты находятся в защищённом конфиге. Предпочтительны абсолютные пути: относительные считаются от рабочего каталога процесса, а не от каталога конфига.

## Подключения и настройки сервиса

### Telegram

| Поле | Тип / значение по умолчанию | Назначение |
| --- | --- | --- |
| `token` | Обязательная непустая строка | Настоящий токен бота. |
| `welcome_message` | Строка, пустая | Ответ на `/start`. |
| `allowed_users` | Массив, пустой | Разрешённые пользователи. |
| `allowed_users[].id` | Целое число | Telegram ID **пользователя**, а не имя, телефон или ID группового чата. |
| `allowed_users[].video_monitoring_enabled` | Boolean, `false` | Начальная персональная настройка; сохранённая имеет приоритет. |
| `poll_timeout_sec` | Целые секунды, `60` | Тайм-аут long polling. |
| `http_timeout_sec` | Целые секунды, `70` | Должен быть больше poll timeout. |
| `proxy.enabled` | Boolean, `false` | Использовать настройки прокси. |
| `proxy.type` | `none` / `socks5` | Прямое подключение или SOCKS5. MTProxy не реализован. |
| `proxy.address` | Строка | SOCKS5 host:port, например `127.0.0.1:1080`. |
| `proxy.username` / `password` | Строки | Необязательная авторизация прокси. |
| `proxy.secret` | Строка | Резервное поле, в поддерживаемых режимах не используется. |

Проверяется ID отправителя сообщения. В группе ответ идёт в группу, но настройка видеоконтроля относится к пользователю. Уведомления и видео отправляются разрешённым пользователям лично. Каждый пользователь должен предварительно открыть личный чат с ботом и нажать **Start / Запустить**.

Получите числовой ID из доверенной существующей интеграции или данных входящего Telegram update. ID самого бота не подходит. После изменения списка пользователей перезапустите SmartHome.

Пример `telegram.proxy`:

```json
{"enabled":true,"type":"socks5","address":"127.0.0.1:1080","username":"","password":""}
```

Прокси влияет только на Telegram. MQTT-правила работают, пока подключение бота повторяется.

### MQTT

| Поле | Тип / значение по умолчанию | Назначение |
| --- | --- | --- |
| `server` | Обязательная строка | URI, например `tcp://192.168.1.2:1883`; порт укажите явно. |
| `login` / `password` | Строки, пустые | Учётные данные брокера. |
| `client_id` | Строка; `SmartHome`, если пустая | Уникален среди одновременно подключённых клиентов. |
| `qos` | Целое 0/1/2; по умолчанию 0 | Для подписок и публикаций. В примерах используется 1. |
| `retained` | Boolean, `false` | Для всех исходящих публикаций, включая команды. Обычно оставляйте false. |
| `base_topics` | Массив строк, без автоматических значений | Имена для шаблонов. По соглашению: индекс 0 — Zigbee-сервис, индекс 1 — голосовая интеграция. |
| `subscribe_to` | Массив строк | Дополнительные общие подписки; шаблоны получают `BaseTopic`. |

Автоматически подписывается `<base_topics[0]>/<zigbee_id>`, дополнительные device `subscribe`, включённые интеграции и явно заданные топики событий. Общая подписка `zigbee2mqtt/#` для обычных правил не нужна.

После переподключения подписки восстанавливаются. Результат публикации/подписки ожидается до пяти секунд. Тайм-аут публикации означает, что доставка может быть неизвестна.

QoS не делает локальные очереди постоянными и не подтверждает физическое выполнение. Постоянного журнала пропущенных событий нет.

`mqtt.retained` относится к исходящим сообщениям. `events[].allow_retained` разрешает реакции на входящие retained-отчёты. Внешние командные интеграции всегда игнорируют retained-команды.

Начальный слеш значим для брокера: `yandex/device` и `/yandex/device` — разные топики. Если нужны оба, укажите оба шаблона.

### Хранение и журналирование

| Поле | По умолчанию | Назначение |
| --- | --- | --- |
| `storage.state_file` | `/var/lib/smarthome/state.json` | Состояние работы. |
| `logging.level` | `info` | `debug`, `info`, `warn`/`warning` или `error`. |
| `logging.file` | Пусто | Необязательный файл журнала с дописыванием. |
| `logging.to_console` | False при заданном файле | Дополнительно выводить в консоль. Без файла консоль включается автоматически. |

В журнале есть время, уровень и место вызова в исходниках. Под systemd можно использовать `file:""` и консоль, тогда хранением занимается journald. Встроенной ротации и переоткрытия журнала по SIGHUP нет. Настройте подходящую внешнюю ротацию либо остановите сервис, переместите журнал и запустите снова. Debug может содержать MQTT payload.

Конфиг, состояние и журнал должны быть разными файлами. Валидатор проверяет прямые конфликты и доступные ему совпадения существующих файлов.

### Подписи

| Поле | По умолчанию / поведение |
| --- | --- |
| `off` / `on` | `ВЫКЛ` / `ВКЛ`. |
| `yes` / `no` | `ДА` / `НЕТ`. |
| `unknown_command` | `Неизвестная команда!`. |
| `datetime_format` | `02.01.06 15:04` — шаблон времени Go. |
| `short_datetime_format` | Допустимо, но сейчас в отображении не используется. |

Настройка labels меняет соответствующие подписи, но не весь интерфейс. Часть служебных сообщений зашита на русском.

Форматы Go используют эталон `Mon Jan 2 15:04:05 MST 2006`. Например, `2006-01-02 15:04:05` задаёт понятную дату со временем. Формат `%Y-%m-%d` относится к другой системе и здесь не подходит.

## Устройства и MQTT-сообщения

| Поле | Назначение |
| --- | --- |
| `id` | Стабильный внутренний ID для ссылок и состояния. |
| `name` | Отображаемое имя. |
| `type` | Используйте `switch`, `sensor`, `alarm` или `virtual`; влияет на отображение и интеграции. |
| `description` | Описательные метаданные. |
| `zigbee_id` | Суффикс топика Zigbee-сервиса: IEEE либо friendly name. |
| `yandex_id` | Необязательный внешний ID. |
| `subscribe` | Дополнительные подписки устройства. |
| `initial` | Начальные поля; применимые сохранённые значения имеют приоритет. |
| `actions` | Именованные действия. |
| `reports` | Вычисляемые публикации при обработке подходящих событий. |
| `fields` | Строковые метаданные для шаблонов. |

`id` и `zigbee_id` — разные значения. При замене оборудования можно сохранить логический ID и сменить суффикс топика.

Типичные отчёты:

```json
{"state":"ON","linkquality":110}
```

```json
{"temperature":23.4,"humidity":48.2,"pressure":1013.25,"battery":87}
```

```json
{"water_leak":true,"battery":96}
```

Для `lumi.weather` проверьте единицы давления в сообщениях сервиса. `pressure_mmhg` ожидает hPa и выдаёт округлённые мм рт. ст. Не преобразовывайте повторно значения, уже выраженные в мм рт. ст.

Для соответствующей сирены Tuya используйте реальные boolean:

```json
{"alarm":true}
```

```json
{"alarm":false}
```

Строковый формат света `"state":"ON"` не означает такой же формат `alarm`. Одной модели `TS0601` недостаточно для определения устройства: производитель, например `_TZE200_t1blo2bj`, и конвертер учитываются в Zigbee-сервисе. Громкость, мелодия и длительность должны соответствовать его writable-параметрам. SmartHome не реализует Tuya datapoints.

Для двухканального реле может понадобиться:

```json
{"state_l1":"OFF","state_l2":"OFF"}
```

Другие модели используют `state_left`/`state_right`. Сначала изучите реальные сообщения и возможности устройства. Отправляйте только нужные изменяемые параметры, а не весь сохранённый отчёт.

`last_seen` меняется при живых подходящих сообщениях. Retained-снимок его не обновляет. Начальная заглушка времени и сохранённая дата не подтверждают, что устройство сейчас на связи.

## Действия, группы и защитные блокировки

### Поля действия

Действия описываются в `devices[].actions.<name>`. Имена задаёте вы: `on`, `off`, `close`, `silence` и другие.

| Поле | Значение |
| --- | --- |
| `title` | Текст результата действия. |
| `set_state` | Необязательная boolean-цель локального `state`. |
| `force` | Выполнить, даже если локальное состояние уже совпадает; по умолчанию false. |
| `publishes` | Последовательные сообщения: `topic` и `payload`. |
| `run_actions` | Последовательные ссылки `device.action` / `group.action`. |
| `set_user_video` | Изменить настройку видеоконтроля вызывающего Telegram-пользователя. |
| `block_when` | Защитные условия до выполнения. |

`set_state` предотвращает повтор одинаковой цели без force. Локальное состояние действия оптимистическое; добавьте обновления из реальных отчётов. При ошибке MQTT откат не должен затирать более новое состояние. Составное действие фиксирует состояние родителя после успешных дочерних действий. Цепочка может выполниться частично.

Для аварийного закрытия и включения сирены используйте `force:true`, чтобы старое состояние не подавляло необходимую команду. Автоматического таймера выключения сирены в SmartHome нет: длительность задаётся устройством либо управляется отдельными командами.

`set_user_video` используйте на отдельном виртуальном устройстве, вызываемом из Telegram. Не объединяйте его с несвязанными публикациями/цепочками; персональной настройке нужен пользователь.

У действия устройства публикации идут до дочерних действий. У явного действия группы дочерние действия идут до публикаций группы. Ошибка не отменяет автоматически остальные операции. Циклические ссылки отклоняются при проверке конфига.

Строковый payload отправляется как текст после подстановок. Объект, массив, число и boolean сначала кодируются в JSON. Для команд устройствам предпочтителен JSON-объект.

### Блокировка открытия воды

Фрагмент внутри действия открытия:

```json
{
"block_when": [
  {"device_id":"leak_toilet","field":"water_leak","value":true},
  {"device_id":"leak_bathroom","field":"water_leak","value":true}
]
}
```

Значения условий должны быть boolean, строкой или числом; для одного защитного поля тип должен быть согласован. Достаточно совпадения одного условия для блокировки. Отсутствующие, неизвестные или несовместимые значения защитного поля также блокируют действие. `force` защиту не обходит.

`initial.water_leak:false` не устанавливает достоверность защитного состояния. После загрузки нужны подходящее сохранённое значение или отчёт. Сообщение только о батарее не подтверждает сухость. Сухой отчёт снимает блокировку этого датчика.

Мокрое состояние сохраняется до обновления. Если датчик перестал передавать сообщения во время протечки, открытие остаётся заблокированным. Проверьте и просушите датчик, получите достоверный отчёт. Ограничения возраста защитного состояния нет: сохранённое сухое значение принимается без подтверждения, что датчик сейчас исправен и на связи.

Защищайте **каждое соответствующее действие открытия**, а не только кнопку меню. Тогда одинаковые блокировки действуют из групп, расписаний и интеграций. Аварийное закрытие и выключение сирены оставляйте без такой блокировки.

### Группы

Неявное групповое действие:

```json
{"id":"lights","name":"Свет","members":["hall_light","kitchen_light"]}
```

Если у группы не задан собственный `off`, вызов `lights.off` выполняет `off` каждого участника. У всех должно быть такое действие.

Явное действие группы:

```json
{
  "id":"water_alarm",
  "name":"Авария воды",
  "members":[],
  "actions":{"trigger":{"run_actions":["water_valve.off","siren.on"]}}
}
```

Явное действие выполняет свои `publishes`/`run_actions` и не обходит `members` автоматически. У группы нет отдельного сохраняемого состояния. Общие поля действий `set_state` и `set_user_video` для групп не выполняются. Шаблоны публикаций группы получают `Group`.

Обычные составные команды идут через общую упорядоченную очередь в памяти. Аварийные правила с уведомлением или подавлением повторного boolean-срабатывания выполняются вне этой очереди. Они не ставятся в обычную FIFO-очередь, но MQTT I/O, занятое устройство или общая блокировка составного действия всё ещё могут задержать выполнение. Переполнение и ошибки журналируются; постоянных повторов доставки нет.

## События и выражения

### Поля и порядок обработки

| Поле | Назначение |
| --- | --- |
| `id` | Уникальный ID события. |
| `on_topic` | Топик/фильтр с MQTT-масками и шаблонами. Пустое значение подходит для любого доставленного сервису сообщения. |
| `device_id` | Контекст состояния, отчётов и шаблонов; нужен для updates. |
| `updates` | Поле состояния → выражение. |
| `when` | Поле сообщения → ожидаемое значение; должны совпасть все условия. |
| `allow_retained` | Разрешить реакции на retained-сообщения; по умолчанию false. |
| `publishes` | Публикации при совпадении реакции. |
| `actions` | Ссылки на именованные действия. |
| `notify` | Telegram-уведомление: `users` и `text`. |

Поле notify.users принимает all (также значение по умолчанию при пустом поле) либо video_enabled. Уведомление отправляется обычным текстом, без разбора HTML. Очередь в памяти вмещает 256 сообщений получателям; переполнение и ошибка отправки журналируются.

События выполняются в порядке конфига. Обновления и отчёты обрабатываются **до** `when` и проверки разрешения retained-действий. Следовательно, when ограничивает реакции, а не updates.

Для события без device_id используйте буквальный топик: при вычислении такого топика во время работы контекст устройства и базовых топиков не передаётся.

Условия проверяют текущее сообщение, не накопленное состояние. Отсутствующее обычное поле не совпадает. Для текстового сообщения есть `$raw`:

```json
{"when":{"$raw":"ON"}}
```

Пример события кнопки:

```json
{
  "id":"button_double",
  "on_topic":"{{index .BaseTopic 0}}/{{.Device.ZigbeeID}}",
  "device_id":"wall_button",
  "when":{"action":"double"},
  "actions":["siren.off"],
  "allow_retained":false
}
```

Названия кнопочных действий зависят от модели/конвертера: проверьте `double`, `single`, `hold` и варианты по каналам в живых сообщениях.

Полный пример объединяет обновления датчика и реакцию `water_leak:true` в одном правиле. Сухой отчёт обновляет состояние и снова разрешает последующее срабатывание.

Повторные успешные boolean-тревоги подавляются до явно противоположного отчёта. Battery-only сообщение защёлку не сбрасывает. После ошибки реакция может повториться на следующем подходящем отчёте; самостоятельного таймера повторов нет. После запуска/переподключения первая подходящая тревога снова допустима.

`allow_retained:true` задавайте осознанно для сохранённых мокрых отчётов. Для кнопок оставляйте false. Retained может обновлять состояние и порождать отчёты даже при запрещённых реакциях.

### Выражения

Значения `updates` и `reports[].expression` — строки.

| Выражение | Результат |
| --- | --- |
| `payload.temperature` | Значение поля верхнего уровня JSON. |
| `payload.battery` | Уровень батареи. |
| `$raw` | Текст payload без крайних пробелов. |
| `$raw_bool` | true/false, on/off, 1/0, ВКЛ/ВЫКЛ → boolean; неизвестный текст не обновляет поле. |
| `eq(payload.state,'ON')` | Равенство; отсутствующее поле не даёт значение. |
| `ne(payload.action,'')` | Неравенство. |
| `and(eq(payload.state_l1,'OFF'),eq(payload.state_l2,'OFF'))` | Логическое И минимум двух boolean-выражений. |
| `pressure_mmhg(payload.pressure)` | Округлённое hPa / 1.333; отсутствующее/некорректное не обновляет поле. |
| `manual` | Строковая константа. |

Произвольного кода, арифметических формул, обхода вложенных объектов, `or` и `not` нет. `payload.a.b` обращается к буквальному ключу верхнего уровня `a.b`, а не к вложенному объекту.

Пробелы по краям всего выражения запрещены; внутри вызовов допустимы. Одинарные кавычки внутри JSON-строк упрощают сравнения.

Частичные живые отчёты объединяют нужные поля в текущем MQTT-сеансе. Раздельные отчёты каналов могут разрешить составное выражение. Отсутствующие операнды не создают ложные false-значения; известный false может определить результат И. Кэш сбрасывается при переподключении; retained не смешивается с живыми данными.

Обновления/отчёты со ссылками на поля вычисляются только при наличии хотя бы одного такого поля в текущем сообщении. Battery-only отчёт не повторяет старое кнопочное действие.

## Шаблоны и исходящие отчёты

Используется Go `text/template` с учётом регистра.

| Переменная | Контекст |
| --- | --- |
| `{{index .BaseTopic 0}}` | Массив базовых топиков. |
| `{{.Device.ID}}` / `{{.Device.Name}}` | Действия/отчёты/подписки устройства и события с device_id. |
| `{{.Device.ZigbeeID}}` / `{{.Device.YandexID}}` | Идентификаторы Zigbee-сервиса и внешней интеграции. |
| `{{index .Device.Fields "room"}}` | Пользовательские метаданные. |
| `{{.Group.ID}}` / `{{.Group.Name}}` | Публикации явного действия группы. |
| `{{.Payload.temperature}}` | Данные события/отчёта; именованные действия не наследуют исходный payload. |
| `{{.RawPayload}}` | Публикации события и уведомления. |
| `{{.Topic}}` / `{{.BoolPayload}}` | Публикации события. |
| `{{.ActionsOK}}` | Результат операций события по его политике выполнения, в уведомлении. |
| `{{json .Payload}}` | JSON-кодирование через функцию `json`. |

Общие подписки получают только `BaseTopic`. Шаблоны топиков должны вычисляться при валидации, поэтому входящие динамические поля в них использовать нельзя. Динамические шаблоны payload/уведомлений вычисляются при сообщении; ошибки ключей и синтаксиса журналируются.

Не вставляйте произвольные неэкранированные строки в JSON вручную. Функция `json` помогает правильно закодировать значения при создании строкового payload.

Отчёт в массиве устройства `reports`:

```json
{
  "name":"temperature",
  "topic":"/{{index .BaseTopic 1}}/{{.Device.YandexID}}/temperature",
  "expression":"payload.temperature"
}
```

Хотя бы одно подходящее событие должно указывать это устройство через `device_id`. Одно описание reports не включает обработку любых топиков.

Для прямого значения используйте `field` вместо `expression`. Если указаны оба, expression приоритетнее. Результат отправляется скалярным текстом, например `23.4` или `true`, без объекта-обёртки. Поле name — метаданные, а не ключ состояния; для сохранения показаний задавайте updates.

## Меню Telegram

`menu.rows` — массив строк клавиатуры. В каждой кнопке выбирайте одну цель:

- `builtin`: `status`, `alarms` либо `batteries`.
- `device_id` с `action`.
- `group_id` с `action`.

```json
{
  "start_command":"/start",
  "rows":[
    [{"text":"Статус","builtin":"status"}],
    [{"text":"Протечки","builtin":"alarms"},{"text":"Батареи","builtin":"batteries"}],
    [{"device_id":"water_valve","action":"off"},{"device_id":"water_valve","action":"on"}],
    [{"group_id":"water_alarm","action":"trigger"}]
  ]
}
```

`text` — буквальная подпись. Без неё создаётся `Имя - ВКЛ/ВЫКЛ` по labels. Подписи должны быть уникальны: пришедший текст определяет действие.

`/start` всегда открывает клавиатуру. `start_command` задаёт дополнительную точную команду. Суффикс имени бота в групповом чате отдельно не разбирается.

`button_width` допустим, по умолчанию 20, но текущий рендерер клавиатуры его не использует.

Встроенные представления:

- **status**: устройства switch с state, настройка видео, home_mode при наличии, первое устройство с температурой, влажностью и давлением.
- **alarms**: поля water_leak устройств `type:"alarm"`, включая неизвестное состояние.
- **batteries**: устройства со значением battery. Кнопка показывается, если battery объявлен в initial либо fields устройства.

Статус показывает локальное состояние, не вызывает немедленный радиоопрос.

## Внешние командные интеграции

Элемент `command_integrations` для yandex2mqtt:

```json
{
  "id":"yandex",
  "enabled":true,
  "topics":[
    "/{{index .BaseTopic 1}}/{{.Device.YandexID}}",
    "{{index .BaseTopic 1}}/{{.Device.YandexID}}"
  ],
  "action_on":"on",
  "action_off":"off",
  "payload_on":["true","on","1","вкл"],
  "payload_off":["false","off","0","выкл"],
  "force":true
}
```

Добавьте `"yandex"` в base_topics под индексом 1 и yandex_id нужным устройствам. Идентификаторы/топики должны совпадать с внешним приложением.

| Поле | Поведение |
| --- | --- |
| `id` | Обязательно при включённой интеграции. |
| `enabled` | По умолчанию false. |
| `topics` | Шаблоны топиков, предпочтительнее одиночного поля. |
| `topic` | Один шаблон, когда topics отсутствует. |
| `action_on` / `action_off` | По умолчанию on / off. |
| `payload_on` | Пустой массив заменяется true/on/1/вкл. |
| `payload_off` | Пустой массив заменяется false/off/0/выкл. |
| `force` | Обходит подавление одинаковой цели, но не защитные условия. |

Вход — скалярный текст/boolean/число; сравнение без учёта регистра после удаления крайних пробелов/кавычек. Объект `{"state":"ON"}` не является скалярной командой. Виртуальные устройства пропускаются; шаблоны, которым не хватает идентификатора, тоже.

Retained-команды всегда игнорируются. Публикуйте команды без retained. Для состояния используйте отдельные топики, например `/yandex/<id>/state`. Защита от петли может пропустить публикации исходной интеграции при обработке её команды; реальные отчёты устройства остаются подходящим источником состояния.

Если интеграция не нужна, задайте `"command_integrations":[]` и уберите Yandex-поля/шаблоны.

## Ежедневные расписания

Элемент `schedules`:

```json
{"id":"light_off_at_night","at":"23:30","action":"living_light.off"}
```

Используется локальное время сервера и формат HH:MM, 24 часа. Отметка «выполнено сегодня» хранится в памяти. Перезапуск в ту же минуту может повторить действие. Пропущенное время не догоняется; ошибка журналируется без автоматической повторной попытки в этот день.

В Linux проверьте время через `timedatectl`. Только для сервиса часовой пояс можно задать командой `sudo systemctl edit smarthome`:

```ini
[Service]
Environment=TZ=Asia/Yekaterinburg
```

Затем `sudo systemctl daemon-reload` и `sudo systemctl restart smarthome`. На машине должны быть данные выбранного часового пояса.

Cron-выражений, дней недели, восхода/заката и индивидуальных поясов расписаний нет.

## Видеоконтроль

Фрагмент для `video_monitoring`:

```json
{
  "enabled":true,
  "lock_file":"/var/lib/smarthome/video.save",
  "check_interval":"1s",
  "delete_lock_file":true
}
```

| Поле | Значение |
| --- | --- |
| `enabled` | По умолчанию false. |
| `lock_file` | Обязательно при включении; содержит путь к готовому видео, не видеоданные. |
| `check_interval` | Строка Go duration, например 500ms/1s, либо целые секунды; по умолчанию секунда. |
| `delete_lock_file` | True забирает/удаляет триггер; false оставляет и не повторяет неизменный экземпляр в текущем процессе. |

Сначала закончите запись видео, потом создавайте триггер. SmartHome нужны права чтения файлов и доступа к каталогам; для забора/удаления триггера — запись в его каталог.

Пример атомарного триггера для одного производителя:

```bash
printf '%s\n' '/var/lib/smarthome/camera.mp4' > /var/lib/smarthome/video.save.tmp
mv /var/lib/smarthome/video.save.tmp /var/lib/smarthome/video.save
```

Выполняйте от пользователя с подходящими правами. Временный и конечный файл должны быть на одной файловой системе. Один путь триггера не является очередью нескольких роликов: новый триггер может заменить ещё необработанный.

Персональное управление получателями — виртуальное устройство:

```json
{
  "id":"video_control",
  "name":"Видеоконтроль",
  "type":"virtual",
  "actions":{
    "on":{"set_user_video":true},
    "off":{"set_user_video":false}
  }
}
```

Добавьте кнопки on/off в меню. Настройка каждого разрешённого пользователя независима и сохраняется; она имеет приоритет над начальным значением конфига.

Видео отправляется в личные чаты пользователей, не в группу с кнопкой. Реализация отклоняет файлы больше `50 * 1024 * 1024` байт и читает файл целиком в память.

При `delete_lock_file:true` триггер удаляется после попытки даже при ошибке отправки или отсутствии включённых получателей. Само видео не удаляется. Неудачные отправки журналируются, постоянного повторения нет. При false после перезапуска оставшийся триггер может обработаться снова.

## Состояние, резервные копии и обновление

Пример структуры состояния:

```json
{
  "devices":{
    "leak_toilet":{"water_leak":false,"battery":94,"last_seen":1790000000},
    "water_valve":{"state":false,"last_seen":1790000000}
  },
  "users":{"111111111":{"video_monitoring_enabled":true}}
}
```

Ключи — внутренние ID устройств и строки с числовыми ID пользователей. Время в примере условное.

Сохранение выполняется через временный файл, sync и атомарное переименование. Не редактируйте состояние при запущенном сервисе. Здесь находятся и оптимистические цели действий, и реальные показания.

| Условие при запуске | Поведение |
| --- | --- |
| Файла нет | Начальные значения; защитные поля неизвестны до подходящих отчётов. |
| Состояние корректно | Загружаются сохранённые значения и пользовательские настройки. |
| JSON повреждён | Содержимое сохраняется в .corrupt-*; используются начальные значения, журнал/уведомление. |
| Файл не читается или восстановление не удалось | Работа без сохранения; исходник не затирается, журнал/уведомление. |

В последнем случае исправьте права/диск и перезапустите для включения сохранения. Новые отчёты могут подтвердить защитное состояние в памяти, но в этом процессе оно не записывается.

Перед изменением конфига или обновлением:

```bash
sudo systemctl stop smarthome
sudo install -d -m 0700 /root/smarthome-backup
sudo cp -a /etc/smarthome.conf /root/smarthome-backup/smarthome.conf
sudo cp -a /usr/local/bin/SmartHome /root/smarthome-backup/SmartHome
```

Если состояние существует:

```bash
sudo cp -a /var/lib/smarthome/state.json /root/smarthome-backup/state.json
```

Установка и проверка нужного бинарника:

```bash
sudo install -o root -g root -m 0755 ./SmartHome /usr/local/bin/SmartHome
sudo -u smarthome /usr/local/bin/SmartHome --check-config --config /etc/smarthome.conf
sudo systemctl start smarthome
sudo journalctl -u smarthome -n 100 --no-pager
```

Используйте схему конфига, поддерживаемую устанавливаемым бинарником. Не восстанавливайте старую сухость датчиков как доказательство безопасности помещения после реальной протечки.

State-файл **не является** резервной копией координатора или базой ключей сопряжения Zigbee. Zigbee-сервис/координатор резервируйте отдельно.

## Добавление и замена устройств

Добавление:

1. Сопрягите и опросите устройство через Zigbee-сервис.
2. Посмотрите настоящий MQTT-топик, поля сообщений и изменяемые параметры.
3. Добавьте стабильный id, имя, type и zigbee_id.
4. Опишите действия и события обновления состояния.
5. При необходимости задайте отчёты/внешние ID.
6. Добавьте ссылки меню, групп и расписаний.
7. Для датчиков воды защищайте все соответствующие действия открытия.
8. Проверьте конфиг, перезапустите и испытайте физическую цепочку.

Изменение JSON не требует пересборки SmartHome. Новый неподдерживаемый радиопротокол всё равно требует поддержки в Zigbee-сервисе.

При замене сохраните логический id, измените zigbee_id и параметры, зависимые от модели. Остальные логические ссылки сохранятся.

Старое состояние не подтверждает состояние нового оборудования. Для защитного датчика остановите сервис, сохраните копию состояния и при необходимости удалите только его устаревшие защитные поля; затем получите новый отчёт. Неизвестное состояние блокирует открытие. Для исполнительного устройства обновите отчёт и физически проверьте переключение.

При смене внутреннего ID исправьте все ссылки. Автоматического переноса state-ключа нет.

## Журналы и диагностика

### Журналы и основные проверки

```bash
sudo journalctl -u smarthome -f
sudo journalctl -u smarthome --since '30 minutes ago' --no-pager
sudo tail -n 100 /var/log/smarthome/smarthome.log
```

Последняя команда относится только к настроенному файлу. Для подробной диагностики задайте logging.level=debug, проверьте конфиг и перезапустите; после сбора верните info.

```bash
sudo -u smarthome /usr/local/bin/SmartHome --check-config --config /etc/smarthome.conf
sudo systemctl cat smarthome
sudo systemctl status smarthome --no-pager
sudo -u smarthome test -r /etc/smarthome.conf
sudo -u smarthome test -w /var/lib/smarthome
```

С клиентами Mosquitto и локальным брокером без авторизации:

```bash
mosquitto_sub -h 127.0.0.1 -p 1883 -t 'zigbee2mqtt/#' -v
```

Для своего брокера задайте его адрес, авторизацию и TLS. Сужайте подписку до нужных устройств. Тестовые команды отправляйте только в проверенные топики исполнительных устройств.

Отдельная проверка boolean-сирены:

```bash
mosquitto_pub -h 127.0.0.1 -p 1883 -t 'zigbee2mqtt/SIREN_TOPIC_SUFFIX/set' -m '{"alarm":true}'
mosquitto_pub -h 127.0.0.1 -p 1883 -t 'zigbee2mqtt/SIREN_TOPIC_SUFFIX/set' -m '{"alarm":false}'
```

Замените суффикс на реальное устройство. Команды без retained.

### Типичные проблемы

| Симптом | Что проверить |
| --- | --- |
| Справка и выход | Добавьте --run. |
| Требуется токен | Нужный конфиг и непустой токен. |
| Unknown field / ошибка JSON | Названия, комментарии, запятые и типы. |
| Invalid expression | Грамматика, кавычки, отсутствие крайних пробелов. |
| Ошибка индекса шаблона | Нужный индекс массива base_topics существует. |
| Цикл перезапусков | Проверка от имени сервиса, чтение конфига, запись журнала. |
| MQTT не авторизуется/отключается | Адрес, порт, пароль, ACL, уникальный client_id. |
| Нет реакции на отчёт | Топик, device_id события, текущие ключи payload, when и отчёты Zigbee-сервиса. |
| alarm: must be true/false | Boolean без кавычек и нужный конвертер сервиса. |
| Открытие заблокировано | Защитный датчик мокрый/неизвестный/отсутствует; прочитайте причину и получите отчёт. |
| MQTT успешен, устройство молчит | Логи Zigbee-сервиса, свойство/endpoint, радио и само устройство. |
| Бот игнорирует | ID отправителя, токен, личный запуск бота, сеть/прокси. |
| Неправильная кнопка | Уникальные подписи; /start после перезапуска обновляет меню. |
| Нет статуса/батареи | Начальные поля и updates; представление поддерживает определённые категории. |
| Старый last_seen | Нет живого подходящего сообщения; retained время не обновляет. |
| Состояние не сохраняется | Права, свободное место, предупреждение запуска; исправьте и перезапустите. |
| Нет видео | Watcher, получатель, готовый файл, права, размер и ошибки Telegram. |
| Queue full | Возможна потеря сообщений/действий; ищите нагрузку и медленный MQTT. |
| Нет веб-страницы | У SmartHome нет веб-сервера; панель есть у отдельного Zigbee-сервиса. |

Защитный отказ не означает ошибку брокера. Подтверждение брокера не доказывает физическое закрытие.

## Приёмка и ограничения эксплуатации

Проверьте на оборудовании:

1. Мокрые и сухие отчёты каждого датчика обновляют нужное логическое устройство.
2. Протечка закрывает нужные клапаны и включает сирену.
3. Мокрые/неизвестные блокировки запрещают все пути открытия.
4. Сухой отчёт снимает правильную блокировку, но не открывает воду без явно заданного действия.
5. Двойное нажатие выключает сирену и не открывает воду.
6. Telegram, кнопки и голос направляют команды правильному оборудованию.
7. Перезапуск и MQTT reconnect не повторяют моментальные команды.
8. Сохранённый мокрый отчёт выполняет нужное правило при allow_retained=true.
9. Файлы состояния/журналов доступны пользователю сервиса.
10. MQTT-автоматика работает при недоступном Telegram.

Ограничения:

- В памяти помещается 1 024 входящих MQTT-задания, 64 ожидающих составных действия и 256 сообщений получателям. Ещё одно составное действие может выполняться. Переполнение и перезапуск могут приводить к потерям.
- Нет постоянного outbox, гарантированной доставки и подтверждения физического положения.
- Блокировки используют известные локальные значения без срока свежести и проверки исправности датчика.
- Цепочки — последовательные операции, не транзакции; частичный результат не откатывается целиком.
- Расписания и видео не имеют постоянного механизма догоняющей доставки.
- Нужны работающие Zigbee-сервис, брокер, сеть и питание; это не независимый аппаратный контроллер защиты.

В критичных установках проверяйте физическое поведение и используйте требуемую независимую защиту.

Race detector требует поддерживаемую локальную платформу и C-компилятор/CGO. Для выполнения cross-build нужен соответствующий целевой компьютер или окружение.

## Уведомления при выполнении действий

У действий устройств и явно заданных действий групп поддерживается поле `notify` с `users` (`all` или `video_enabled`) и шаблоном `text`. Уведомление отправляется после завершения всей цепочки, независимо от источника команды. `.ActionsOK` позволяет различать успех и неполное выполнение. Пропущенное действие «уже выполнено» не создаёт новой рассылки. Подробная настройка режима «МЫ УШЛИ» — в [NOTIFICATIONS.ru.md](NOTIFICATIONS.ru.md).

## Общий видеоконтроль

Поле `set_all_users_video` в действии устройства или группы включает (`true`) либо выключает (`false`) доставку видео всем пользователям из `telegram.allowed_users`. Оно не зависит от источника команды. Для связи с режимом «МЫ УШЛИ» добавьте его к `home_mode.actions.on` и `home_mode.actions.off` соответственно, сохранив остальные настройки. Скрипт `scripts/enable-away-video.py` создаёт исправленную копию текущего конфига и убирает распознанные старые персональные команды из этих цепочек. Инструкция — [AWAY_VIDEO.ru.md](AWAY_VIDEO.ru.md).

Прежние персональные действия `set_user_video` и явный `video_user_id` поддерживаются. В одном действии нельзя смешивать общий и персональный режимы.
